## Your task: tamper-ledger, a hash chain over the ledger and `theseus ledger verify`: its audit log can't be quietly edited (theseus-bmkxk)

Branch: `cloud/20261011-tamper-ledger`. Every commit's subject carries `theseus-bmkxk`. Deadline for the report: 4 hours
after you start.

**Why this work exists.** The killer-features plan (§4.9, row R25): "Its audit log can't be quietly edited." Every
state transition, loop, approval and spend is a ledger row (`crates/theseus-core/src/ledger.rs`: `LedgerRow {at_unix_ms,
kind, session_id, turn_id, data}`, stored as JSON records of kind `LEDGER` in the embedded store,
`crates/theseus-store/src/record.rs`), written in WAL frames whose checksums catch corruption but not an edit: anyone
who can write the store can change a row, recompute the frame's checksum, and nothing says so. A chain of digests
makes an edit, a deletion or a reorder visible. It is cheap, and it is a compliance story.

**What to build:**
1. **The chain.** Each ledger row carries `chain`: SHA-256 over (the previous row's `chain` ‖ this row's canonical
   bytes), computed by the store's single writer in WAL order, so concurrent appenders can't interleave it
   differently. Hash with a crate already in the workspace (check `Cargo.lock` first: `sha2` is likely there; no new
   dependency without saying why). The canonical bytes are defined once (the row's stored JSON as written, or a fixed
   field order: say which, and why it is stable across serde versions).
2. **Its start on an existing store.** Rows written before this build have no `chain`. The first write after upgrade
   appends one `ledger.chain_started` row (the count and last position of unchained rows, and a digest over them all,
   so the old history is pinned too), and the chain runs from there. A fresh store starts with it.
3. **`theseus ledger verify [--since POS] [--json]`** (and a read-only protocol method in a new module,
   `ledger.verify`; `theseus-protocol/src/lib.rs` has 15 lines of room): walks the rows in WAL order, recomputes, and
   prints either `ledger ok: 1,204,331 rows chained since <time>, head 3fa1…` or the **first broken link** (its position,
   time, kind, and whether it was edited, removed or reordered, as far as the walk can tell), with exit status 0 / 1. It
   streams (constant memory) and answers on a million rows in seconds: measure it.
4. **The head, anchored.** `theseus ledger head` prints the current head digest and position; health shows the head's
   short form; when durability ships the store off the machine (`[aws.accounts.*] durability`), the head goes with each
   segment, so an edit that rewrites the whole chain from some row onward is caught against a head recorded earlier.
   Say plainly in the docs what the chain can and cannot catch: an edit, a deletion or a reorder, yes; a forger who
   rewrites every later row with Theseus's own code and no earlier head to compare, no.
5. **The cost, stated.** In the report: bytes per row added (the `chain` field, as stored), the store's growth on a
   representative store (the theseus-sim stores or the bench's), the writer's added time per row and per frame, and
   `theseus-sim bench lifecycle --runs 10 --check` before and after (the gate's budgets must still pass: 5 frames on a
   plain turn, 9 on a tool-call turn; this adds no frame, only bytes and one hash per row).

**The store's format.** A new field on a stored record: bump `MANIFEST_FORMAT` by one from main's number as you clone
it (AGENTS.md, "The store's version rule"), with the old layout's literal sample in theseus-core's `tests_layouts.rs`;
the bump changes `core_output.txt` and `kernel_frames.txt` (two goldens). The `standing` row bumps it and joins before
you launch; `fork-a` may bump it too, and the maintainer renumbers at the merge. If the chain can live with no record
change (for example a per-frame digest the WAL already has room for), weigh it and say why you chose as you did.
