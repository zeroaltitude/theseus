## What I found
- candle splits each matmul into `RAYON_NUM_THREADS` jobs (`candle-core` utils `get_num_threads`, read at every matmul) and gemm runs them with `into_par_iter()` in the pool its caller is in. So a second, one-thread pool does bound the compute to one thread: the four jobs of a matmul run in turn on it, and no other thread computes. Counted by per-thread CPU time of the whole process: busy lane 1 thread, full pool 4. Splitting four ways on one thread costs about 3 % over unsplit at a query's shapes (37 tokens, 768/3072-d: 21.9 s against 21.1 s for the same work), but about 2x at a large M (64 x 768 x 3072), so no env-var juggling was done.
- The brief's recall deadline is the core's: the tender is never told it. A recall closes its connection at the deadline and uses its words answer. So a queued query leaves the line when `gone` says so (`Missed::Gone`, the existing GONE error that the core already treats as words only), and one with no deadline (CLI search) leaves at `MAX_WAIT` = 1 s with the vector source in `skipped` (words alone, no error).
- Existing test `vtests::a_query_holds_the_backfill_while_it_embeds` blocks the full pool, so it must run with the gate open: it now calls the test-only `Gate::force(Some(false))` (otherwise a busy CI machine sends the query to the one-thread pool and the test passes for the wrong reason or fails).

## Left / design notes
- `MAX_WAIT` (1 s) is a fixed constant for callers with no deadline; if the owner wants the recall deadline passed to the tender instead it is a protocol field (`wait`) and a one-line change.
- A timing line for the gate's wait (`gate_ms` in `IndexTimings`) was not added (another wire field); the status counts say how many waited.
- Docs: the maintainer may note in the spec's M6 item and docs/status.md that `query_threads = 0` means 4 again, gated.
